Sí. En ese caso no te recomiendo una colección productos sencilla con campos como nombre, precio, stock, categoria, porque cuando entren carnes, abarrotes, bebidas, medicamentos, refacciones, ropa, productos por peso, productos con lote, productos con serie, combos, servicios, etc., terminarás modificando la estructura constantemente.

Yo construiría Y Soft desde ahora como un sistema de inventario genérico, donde el producto es una entidad flexible y el inventario depende de ubicaciones, unidades, lotes/series y movimientos.

13. Inventario actual

inventory_balances es la fotografía actual.

inventory_movements es la historia.

inventory_balances
       ↓
"¿Cuánto tengo ahora?"

inventory_movements
       ↓
"¿Cómo llegué a esa cantidad?"

Esta separación es fundamental para que el sistema pueda crecer.

La regla arquitectónica principal

No diseñes Y Soft pensando en “productos de abarrotes”.

Diseñémoslo pensando en:

> “Y Soft puede administrar cualquier artículo que tenga identidad, unidad, precio, existencia, ubicación y reglas de control.”



Entonces mañana puedes meter carne por kilogramo, refrescos por caja, ropa por talla/color, electrónicos por número de serie, productos con caducidad, refacciones, paquetes, combos o incluso servicios, sin tener que reconstruir la base de datos.

Y para tu caso particular, la separación que considero más importante es:

Producto → Ubicación → Existencia → Movimiento → Operación → Usuario → Permiso → Auditoría.

Esa cadena es la que hará que el sistema pueda crecer sin convertirse en un inventario frágil.
